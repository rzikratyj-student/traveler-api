# Посібник до захисту TravelerAPI

Мета документа — щоб ви могли пояснити кожне рішення власними словами і змінити його самостійно.
Посилання `файл:рядок` відповідають гілці `review/fixes`. Якщо код змінюватиметься, рядки зсунуться,
тому орієнтуйтеся на назви функцій.

## 1. Структура проєкту

```text
app/
  __init__.py     порожній; робить app пакетом, щоб працював імпорт "from app.plans import ..."
  main.py         конфігурація БД, FastAPI, /health, обробники помилок, OpenAPI
  plans.py        моделі й маршрути планів + спільні правила валідації (StrictInput)
  locations.py    моделі й маршрути локацій, блокування плану, visit_order
docs/
  schema.sql      таблиці, обмеження, індекси, тригери (для нової БД)
  travel_api_swagger.json   контракт API (OpenAPI 3.0)
  schema.mermeid / schema.png   ER-діаграма
migrations/001_location_version.sql   додає locations.version у стару БД
scripts/update_openapi.py   програмно вносить зміни в контракт
scripts/load_test.py        навантажувальний тест
tests/*.hurl                HTTP-сценарії
tests/test_*.py             pytest: конкурентність, обробка помилок, відповідність контракту
```

Стек: FastAPI (маршрути), Pydantic (перевірка JSON), SQLAlchemy **Core** (engine, пул з'єднань,
транзакції, текстовий SQL через `text()`), psycopg 3 (драйвер PostgreSQL), Uvicorn (HTTP-сервер).
**ORM тут не використовується**: таблиці не описані Python-класами, SQL написано вручну.

## 2. Шлях HTTP-запиту

Приклад: `PUT /api/travel-plans/{id}` з тілом `{"budget": 2500, "version": 1}`.

1. **Uvicorn** приймає TCP-з'єднання і розбирає HTTP.
2. **FastAPI** знаходить маршрут `update_plan` (`app/plans.py:170`). Підключення маршрутів: `app/main.py:140`,
   `app.include_router(...)`.
3. FastAPI перетворює `{id}` на `UUID`. Якщо формат неправильний, виникає `RequestValidationError`,
   і обробник `validation_error` (`app/main.py:89`) повертає 400.
4. Тіло JSON перевіряється моделлю `PlanUpdate` (`app/plans.py:71`). Невідоме поле, `version` ≤ 0
   або `title: null` дають той самий шлях і 400.
5. Код функції будує `UPDATE ... WHERE id = :id AND version = :expected_version` і виконує його
   в транзакції `engine.begin()`.
6. Результат:
   - рядок оновлено → `serialize_row` (Decimal → float) → JSON 200;
   - 0 рядків → `HTTPException(409 або 404)` → обробник `http_error` (`app/main.py:75`) формує JSON;
   - порушено CHECK у БД → `IntegrityError` → `database_validation_error` (`app/main.py:97`) → 400;
   - будь-яка інша несподівана помилка → `internal_error` (`app/main.py:125`) → 500 `{"error": "Internal server error"}`,
     а деталі потрапляють лише в лог сервера.

## 3. SQL-схема (`docs/schema.sql`)

- `travel_plans.id`, `locations.id` — `UUID DEFAULT gen_random_uuid()`.
- `locations.travel_plan_id REFERENCES travel_plans(id) ON DELETE CASCADE`: видалення плану видаляє його локації в БД.
  Тому `delete_plan` виконує лише один `DELETE`.
- CHECK-обмеження: непорожні назви, дати (`end_date >= start_date`), бюджет ≥ 0, координати в межах, `version > 0`.
- `UNIQUE (travel_plan_id, visit_order)` — **остання лінія захисту**: два однакові номери в одному плані неможливі за будь-якого способу запису.
- Тригер `auto_assign_location_order` заповнює `visit_order = MAX + 1`, якщо його не передали. Він потрібен для прямих SQL-вставок.
  API передає номер саме, тому для запитів через API тригер нічого не робить.
- Тригер `update_travel_plans_updated_at` оновлює `updated_at` при кожному `UPDATE` плану.
- `locations.version` додано у `ec1f488`. Для старих баз є `migrations/001_location_version.sql`
  (ідемпотентна, тобто повторний запуск нічого не ламає).

## 5. Валідація

- `ConfigDict(extra="forbid", str_strip_whitespace=True)` у `StrictInput` (`plans.py:34`): невідомі поля → 400,
  пробіли по краях обрізаються, тому `"   "` стає порожнім рядком і не проходить `min_length=1`.
- `field_validator("*")` → `reject_nul_character`: PostgreSQL не може зберегти `\u0000`, раніше це давало 500.
- `version`, `visit_order`: `strict=True` (лише JSON-ціле, не `true` і не `"1"`), `le=INT32_MAX`
  (більші числа не вміщаються в `INTEGER` PostgreSQL).
- `is_public`: `strict=True` (лише `true`/`false`).
- Дати: `reject_number` (`plans.py:24`) не дає Pydantic перетворити `0` на `1970-01-01`.
  `strict=True` для дат не підходить: FastAPI валідує вже розібраний JSON у Python-режимі, де строгий режим відкидає навіть ISO-рядки.
- Локації: координати −90..90 / −180..180 з точністю до 6 знаків, дати лише з часовим поясом,
  `departure_date ≥ arrival_date` (`LocationFields.validate_dates`).
- **Пропущене поле ≠ `null`.** `model_dump(exclude_unset=True)` повертає лише ті поля, що були в JSON.
  `{"description": null}` очищає опис, а відсутній `description` лишає його без змін.
  Для обов'язкових колонок (`title`, `currency`, `is_public`, `name`, `visit_order`) явний `null` відхиляється.
- **Часткове оновлення і збережені значення.** Для плану дату перевіряє CHECK у БД:
  `{"end_date": "2025-06-01"}` при збереженому `start_date = 2025-06-10` → 400.
  Для локації код об'єднує збережений рядок із новими полями і перевіряє результат моделлю `LocationCreate` (`locations.py:138`).

## 6. Транзакції

`with engine.begin() as connection:` відкриває транзакцію і бере з'єднання з пулу.
Якщо блок завершився без помилки, виконується COMMIT. Якщо виникла помилка (зокрема `HTTPException(409)`), виконується ROLLBACK.
Тому відхилений запит нічого не змінює. Рівень ізоляції — типовий для PostgreSQL **READ COMMITTED**.

`engine.connect()` у `list_plans` і `/health` використовується лише для читання. Окремий `SELECT`
сам по собі бачить узгоджений знімок даних.

**Тривалість блокувань:** блокування рядків тримаються до COMMIT/ROLLBACK, тобто лише кілька мілісекунд виконання одного обробника.
Між запитами клієнта нічого не блокується, тому «чашка кави» з PDF нікого не затримає.

## 7. Блокування та version — розв'язання проблем 1–3 з PDF

### Проблема 1: одночасне оновлення плану (оптимістичне блокування)

```python
# app/plans.py, update_plan
"UPDATE travel_plans SET budget = :budget, version = version + 1"
" WHERE id = :id AND version = :expected_version RETURNING *"
```

Два клієнти прочитали `version = 1`. Перший `UPDATE` блокує рядок. Другий чекає, а після COMMIT першого
PostgreSQL **повторно перевіряє** умову `WHERE` на новій версії рядка: тепер `version = 2`, тож умова хибна і змінено 0 рядків.
Код бачить `row is None`, читає поточну версію і повертає 409 з `current_version`.
Переможець збережений, версія збільшилася рівно на 1. Тест: `test_concurrent_plan_updates`.

**Навіщо `version`, якщо є `updated_at`?** Час має обмежену точність і може збігтися у двох змін.
Годинники різних серверів розходяться, а `NOW()` в одній транзакції незмінне. Ціле число,
яке змінюється при кожному оновленні, однозначне й дешеве для порівняння.

### Проблема 2: одночасне додавання локацій

Самого `SELECT MAX(visit_order) + 1` недостатньо. Дві транзакції одночасно прочитають `MAX = 2`,
обидві візьмуть 3, і одна з них упаде на UNIQUE (а без UNIQUE з'явився б дублікат).

Розв'язання (`create_location`):
1. `lock_plan` → `SELECT id FROM travel_plans WHERE id = :id FOR UPDATE` (`locations.py:65`).
   Друга транзакція **чекає**, поки перша завершиться.
2. Після COMMIT першої друга читає вже новий `MAX` (у READ COMMITTED кожен оператор бачить свіжі закомічені дані).
3. UNIQUE — страховка на випадок помилки в коді або прямих записів у БД.

Ролі: **блокування** забезпечує, що всі паралельні запити успішні й отримують 1..N.
**UNIQUE** гарантує, що дублікатів не буде за жодних умов.
Перевірено мутацією: без `FOR UPDATE` тест падає 5/5 разів із 400, хоча дублікатів у БД немає
(`docs/verification.md`, §4). Тест: `test_concurrent_location_creation` (10 паралельних запитів).

Прямі SQL-вставки без блокування: тригер рахує той самий `MAX + 1`, друга вставка чекає першу й отримує `UniqueViolation`.
Тобто для прямих записів гарантується лише відсутність дублікатів, а не успіх обох вставок.

### Проблема 3: одночасне оновлення однієї локації

Обрано варіант (а) з PDF: **власна `version` у кожної локації** (коміт `ec1f488`). Блокування рядка плану
в `update_location` не означає спільної версії на весь план, воно лише впорядковує зміни локацій
одного плану (зокрема `visit_order`).

`update_location`: заблокувати план → заблокувати локацію (`FOR UPDATE`) → порівняти `version`
→ 409 з `current_version` або `UPDATE ... version = version + 1`.

Сценарій з PDF: A змінює бюджет, B — нотатки, обидва з `version = 1`. Один отримує 200, інший 409.
Після повтору з актуальною версією збережено **обидві** зміни. Тести: `test_concurrent_location_updates`, `tests/location-version.hurl`.

### Порядок блокувань і дедлоки

Усі операції з локаціями спершу блокують **план**, потім локацію. `DELETE` плану блокує план, потім каскадно локації.
`UPDATE` плану бере блокування рядка плану, несумісне з `FOR UPDATE` і `FOR SHARE`.
Порядок завжди «план → локації», тому циклічного очікування (дедлоку) між цими операціями немає.

### Узгоджене читання плану з локаціями

`get_plan` бере `FOR SHARE` на рядок плану. Поки читання не завершилося, зміни локацій цього плану
(їм потрібен `FOR UPDATE` плану) чекають. Тому план і список локацій у відповіді узгоджені.
Ціна: читачі й записувачі одного плану ненадовго чекають одне одного.
Альтернатива без блокувань — транзакція `REPEATABLE READ READ ONLY` (один знімок на обидва `SELECT`).

## 10. Безпека

- SQL injection: значення завжди передаються параметрами (`:name`), а назви колонок беруться лише з полів моделі Pydantic.
- XSS: API віддає JSON, а не HTML. Екранувати текст при виведенні має клієнт; текст навмисно не «очищується».
- CSRF: немає cookie-автентифікації, тому браузер нічого не підставить сам.
